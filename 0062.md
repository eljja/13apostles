### [3] Incremental Residue-Sieved Neighborhood Exploration (IRSNE)
```markdown
## Candidate Name
Incremental Residue-Sieved Neighborhood Exploration (IRSNE)

### Core Change
Shift the search paradigm from "independent random sampling" to "local neighborhood exploration with incremental single-precision sieving". 

Instead of generating a completely new random $N$-bit integer and performing 168 expensive arbitrary-precision modulo operations (`candidate % p`) on every attempt:
1. Generate a single random base candidate $C$ of the target bit-size once per generation.
2. Pre-calculate and cache the remainders $R_p = C \pmod p$ for all $p$ in `SMALL_PRIMES`. This is a one-time cost per generation.
3. Explore the local neighborhood of $C$ by testing candidates of the form $C + d$, where $d$ is an even offset ($d = 0, 2, 4, 6, \dots$).
4. For each offset $d$, verify small-prime divisibility using the cached remainders: if $(R_p + d) \pmod p == 0$ for any $p$, the candidate is composite. This division is performed entirely on standard machine-sized integers, bypassing Python’s slow arbitrary-precision division.
5. If an offset $d$ survives this ultra-fast incremental sieve, construct the actual large integer $C + d$ and perform the Miller-Rabin test.

### Expected Impact
This paradigm shift directly addresses the cubic scaling bottleneck ($O(k^3)$) of large-integer arithmetic:
- **Near-Zero Trial Division Cost:** Replaces hundreds of expensive arbitrary-precision divisions on 1024+ bit integers with cheap, single-precision additions and modulos on machine-sized integers.
- **Minimal Entropy Overhead:** Reduces the calls to `random.getrandbits` from thousands of times to exactly once per generation, eliminating a major Python-level bottleneck.
- **Explosive Throughput in Later Generations:** By making the pre-sieve virtually free, the search loop can discard millions of composite candidates in milliseconds, reserving CPU cycles exclusively for Miller-Rabin tests on high-probability candidates. This will allow the organism to comfortably breach the 4096-bit ceiling within the 5.0-second budget.

### Required Cost
- **Computational:** A one-time setup cost of 168 modular reductions of a large integer per generation. Memory footprint is trivial (storing 168 small integers in a list).
- **Development Time:** Moderate (~20–30 minutes). Requires refactoring `search_one_generation` to maintain residue states and iterate over offsets.
- **Complexity:** Moderately higher control flow, but remains entirely self-contained within the search execution path.

### Key Risks
- **Local Sparsity / Clustering:** In the astronomical odds that a base candidate $C$ lands in an abnormally large prime desert, the loop might test many offsets. However, by the Prime Number Theorem, a prime is expected within approximately $\ln(2^k)$ steps (e.g., ~1400 steps for 2048 bits), which is traversed in microseconds using IRSNE.
- **Strict Target Bit-Size Violations:** If the offset $d$ grows too large, it could theoretically overflow the target bit boundary. This is easily mitigated by limiting the maximum offset $d$ to prevent bit-length modification.

### Experiment Method
```
