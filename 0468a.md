This uses the existing `SIEVE_DATA_CONSTANTS` but increases the number of prime factors used in the `math.gcd` product check as the computational cost of Miller-Rabin modular exponentiation grows quadratically.

### Expected Impact
This improves "Efficiency" and "Ceiling Growth." As bit-size increases, the cost of an `is_probable_prime` failure becomes significantly higher. By increasing the sieve density for large bit-sizes, we trade a negligible amount of pre-computation (GCD against a larger constant) for a higher rate of "hard rejection" of composite candidates, preventing expensive Miller-Rabin calls on numbers that are obviously composite.

### Required Cost
- **Computational:** Minimal; the `FULL_SIEVE_PRODUCT` is already computed. Using larger products in `math.gcd` for larger bit-sizes adds negligible cycles.
- **Development:** Minimal (changing the `PRODUCT` selection logic to be a function of `bit_size`).
- **Maintenance:** Near zero; the constants are already present.

### Key Risks
- **Overhead:** If the `sieve_depth` is set too high for very small bit-sizes, the cost of GCD might eventually outweigh the cost of Miller-Rabin.
- **Mitigation:** The thresholding ensures this only triggers when `bit_size` is large enough that Miller-Rabin cost dominates.

### Experiment Method
Run the organism for 50 generations with fixed sieve-depth and 50 with ASDB. Compare `total_attempts` and `average_mr_calls_per_prime` for bit-sizes $\ge 2048$.

### Success Criteria
1. **Efficiency Gain:** A >10% reduction in `total_attempts` for generations $\ge 2048$ bits.
2. **Throughput:** An increase in the number of successful prime discoveries within the 5.0s window.
3. **Fitness:** Improvement in the fitness function numerator/denominator ratio.

### Rollback Conditions
- If the time to generate a single candidate (the `make_candidate` loop) increases by more than 5%.
- If the `success_count` does not show improvement in high-bit generations.
- If any instability in prime detection arises.
