Adaptive Multi-Threaded Search Orchestration

Modify `PrimeOrganism.search_one_generation` to utilize `concurrent.futures.ThreadPoolExecutor` to parallelize the `is_probable_prime` test across available CPU cores. Instead of testing candidates sequentially, the search loop will spawn a pool of workers that concurrently test candidates until the first prime is found, at which point the pool is shut down to conserve resources.

### Expected Impact
This significantly improves **Discovery Speed** and **Efficiency**. Miller-Rabin modular exponentiation is CPU-bound; by parallelizing, we can effectively utilize multiple cores to perform simultaneous probabilistic primality tests. This increases the total number of candidates evaluated per unit of wall-clock time, allowing the organism to bypass the time-limit bottleneck in higher-bit generations and achieve higher **Ceiling Growth**.

### Required Cost
- **Computational:** Negligible; the overhead of thread management is offset by the massive gains in raw throughput.
- **Development:** Moderate; requires refactoring the synchronous search loop into a thread-safe task distribution model.
- **Maintenance:** Low; standard `concurrent.futures` implementation is well-documented and robust.

### Key Risks
- **Resource Contention:** Over-provisioning threads could cause CPU context-switching overhead, potentially slowing down the system if the thread pool size exceeds the physical core count.
- **Thread Safety:** Ensuring the `deadline` and `bit_size` parameters are shared correctly across threads without race conditions or performance-degrading locks.
- **Premature Termination:** The risk that multiple threads might find a prime nearly simultaneously, requiring a clean "interrupt" to stop all workers.

### Experiment Method
Run the organism 20 times in a controlled environment with fixed thread counts (e.g., 2, 4, 8) and measure the total number of successful prime discoveries and the time taken for the highest bit-size generation. Compare against the synchronous `047.py` baseline.

### Success Criteria
1. **Throughput Increase:** At least a 1.5x increase in the total number of Miller-Rabin tests completed within the 5-second window.
2. **Ceiling Growth:** Successful identification of a higher bit-length prime in at least 70% of runs compared to the single-threaded baseline.
3. **Stability:** No threading-related exceptions or deadlock hangs during the 5-second lifespan.

### Rollback Conditions
- If the CPU load causes excessive system-wide latency or if thread overhead leads to a drop in the successful discovery rate.
- If the `success_count` fails to show an improvement over the synchronous implementation.
- If the system fails to correctly terminate worker threads within the time budget, leading to zombie process issues.

- **Sieve Diminishing Returns:** If the bit-size is very small, checking 669 primes would be slower than just running the Miller-Rabin test once, which is why the tiered depth is critical.

### Experiment Method
